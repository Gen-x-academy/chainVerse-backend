# Scholarship Finance

Backend module: `src/scholarship-finance/` (`ScholarshipFinanceModule`).

Covers:

| Issue | Capability |
| ----- | ---------- |
| #1164 | Per-program double-entry ledgers |
| #1165 | Treasury reconciliation, solvency gate, discrepancy alerts |
| #1162 | Payout intents with failure classification and controlled retry |
| #1163 | Durable recipient payment receipts with on-chain evidence |

Interactive API docs are generated by Swagger at `/api` under the
`Scholarship Finance — *` tags.

---

## 1. Domain model

```
Organization (tenant)
└── ScholarshipProgram          one asset, one network, one treasury account
    ├── LedgerEntry*            immutable, balanced journal
    ├── PayoutIntent*           one per (award, installment)
    │   └── attempts[]          one per transaction envelope
    ├── PaymentReceipt*         one per successful PayoutIntent
    ├── ReconciliationRun*      immutable comparison snapshot
    └── ReconciliationAlert*    operator-facing, never edits the ledger
```

Awards and installments are referenced by id (`awardId`, `installmentId`).
This module does not own award eligibility. It only records the money.

### Amounts

All amounts are fixed-point with 7 decimal places (Stellar stroops). The API
accepts and returns decimal strings (`"1250.5"`), and the database stores
integer minor units as strings. Floating point is never used.

### Chart of accounts

| Account          | Normal side | Meaning |
| ---------------- | ----------- | ------- |
| `treasury`       | debit       | Funds held in the program's on-chain treasury account |
| `program_fund`   | credit      | Unencumbered funds available to reserve |
| `reserved`       | credit      | Earmarked for scholarships not yet awarded |
| `awards_payable` | credit      | Awarded to recipients, not yet paid |

Invariant: `treasury = program_fund + reserved + awards_payable`.

### Entry types

| Type                  | Debit            | Credit           | Notes |
| --------------------- | ---------------- | ---------------- | ----- |
| `funding`             | treasury         | program_fund     | requires `transactionHash` |
| `reservation`         | program_fund     | reserved         | **solvency-gated** |
| `reservation_release` | reserved         | program_fund     | |
| `award`               | reserved         | awards_payable   | **solvency-gated**, requires `awardId` |
| `award_cancellation`  | awards_payable   | reserved         | requires `awardId` |
| `disbursement`        | awards_payable   | treasury         | posted automatically by successful payouts |
| `refund`              | program_fund     | treasury         | back to the sponsor, requires `transactionHash` |
| `recovery`            | treasury         | program_fund     | clawback, requires `transactionHash` |
| `adjustment`          | explicit lines   | explicit lines   | requires `reason` (≥ 10 chars) |
| `reversal`            | mirror of original | mirror of original | via the reversal endpoint only |

Rules enforced on every posting:

- sum(debits) = sum(credits) > 0, and every line is > 0.
- `reference` is unique per organization. Replaying an identical request
  returns the original entry with `replayed: true`. Reusing a reference with a
  different payload returns `409 BIZ_LEDGER_REFERENCE_CONFLICT`.
- No account may go negative on its normal side (`BIZ_PROGRAM_INSOLVENT`).
- Postings for a program are serialised with a short-lived lease on the
  program document, so balance checks cannot race.
- Entries are immutable. Mongoose hooks reject update/delete, and corrections
  are made with a reversal plus a new entry. Each entry can be reversed only
  once, and a reversal cannot itself be reversed.
- Suspended programs reject new reservations and awards. Closed programs
  accept only wind-down types (release, cancellation, disbursement, refund,
  recovery, adjustment, reversal).

Balances are always derived from the journal, never stored.

## 2. Reconciliation and solvency

A reconciliation run compares:

- **external**: the treasury account balance from Horizon, or a manual
  snapshot for programs with `externalBalanceSource: "manual"`;
- **ledger**: derived balances as of the run time (entries both effective and
  recorded by then);
- **in-flight**: payouts submitted to the network whose outcome is unknown.

It computes:

- `drift = external − ledger.treasury`. A shortfall up to the in-flight
  amount counts as *explained*; anything else is *unexplained drift*.
- `solvencyMargin = external − explainedDrift − (reserved + awards_payable)`.

Discrepancies (all **critical**):

| Type               | Condition |
| ------------------ | --------- |
| `ledger_integrity` | an entry does not balance, or the accounting identity fails |
| `negative_balance` | any account below zero |
| `balance_drift`    | unexplained drift ≠ 0 |
| `insolvency`       | solvency margin < 0 |
| `payout_posting_failed` | a payout succeeded on-chain but its disbursement could not be posted |

Each discrepancy opens an alert, or refreshes the program's active alert of the
same type (`occurrences`, `lastRunId`). It also emits
`scholarship.reconciliation.alert-raised`. **Alerts never modify the ledger.**
Operators post corrective adjustments or reversals themselves, then resolve
the alert with a note.

**Repeatability.** Runs are immutable and record their inputs: `asOf`, entry
count, last entry id, external balance and source, and in-flight total.
`POST …/reconciliations/:runId/replay` recomputes a run from those inputs and
reports whether every figure matches.

**Solvency gate (before new awards).** Every `reservation` and `award` is
checked by `SolvencyGuardService` before posting. The entry is refused when:

1. an unresolved critical alert exists for the program; or
2. the latest run is missing or older than `SCHOLARSHIP_RECONCILIATION_MAX_AGE_MS`.
   Horizon-backed programs are reconciled inline first. Manual programs must
   record a fresh snapshot; or
3. the latest run found discrepancies; or
4. `min(verified external, ledger treasury) − obligations − new obligation < 0`.

The gate fails closed. If Horizon is unreachable, new awards are refused
(`503 SYS_HORIZON_UNAVAILABLE`).

## 3. Payouts and failure recovery

The backend **never holds signing keys**. A separate custody signer service,
authenticated with a platform-admin token, builds, signs and submits
envelopes, then reports back.

```
operator ── POST payouts ─────────────► intent(pending) + attempt#1(ready)
signer   ── GET  payout-signer/attempts ► instructions (source, destination, asset, amount, memo, maxTime)
signer   ── POST …/attempts/:id/submission  {envelopeHash, transactionHash}  → submitted
signer   ── POST …/attempts/:id/result      {outcome, transactionHash | resultCodes | signerError}
             succeeded → verified on Horizon → disbursement entry → receipt → intent(succeeded)
             failed    → classified → intent(failed) + diagnostics (+ nextRetryAt when automatic)
operator ── POST payouts/:id/retries   {note, destination?} → attempt#n(ready)
```

- **Same intent, new envelope.** Every attempt shares the intent id, amount
  and memo (`SCH-<24 hex>`). An envelope or transaction hash already used by
  any attempt is rejected (`BIZ_PAYOUT_ENVELOPE_REUSED`).
- **No double payment.** A new attempt is created only after the previous one
  is dead: its transaction failed on-chain, or it is absent from Horizon after
  its `maxTime` plus 60s grace. If it succeeded on-chain, the retry is refused
  and the expiry sweep records the success.
- **Eligibility preserved.** Failures and cancellations never touch the award
  or its `awards_payable` balance. Only a verified success posts the
  disbursement.
- **Creation guard.** An intent is accepted only if the award's outstanding
  `awards_payable` covers this amount plus the award's other open intents.

Failure classification (from Horizon `result_codes` or the signer error):

| Category             | Typical codes | Auto retry | Operator action |
| -------------------- | ------------- | ---------- | --------------- |
| `missing_trustline`  | `op_no_trust`, `op_not_authorized`, `op_line_full` | no | recipient adds or authorizes the trustline, then retry |
| `bad_destination`    | `op_no_destination`, `op_malformed` | no | retry **with a corrected destination** (recorded in `destinationHistory`) |
| `insufficient_funds` | `op_underfunded`, `tx_insufficient_balance`, `tx_insufficient_fee`, `op_src_no_trust` | no | top up the treasury, reconcile, retry |
| `network_expiry`     | `tx_too_late`, expired or unsubmitted attempt | yes | none |
| `transient`          | `tx_bad_seq`, `tx_internal_error`, 5xx | yes | none |
| `unknown`            | anything else | no | inspect, then retry |

Automatic retries back off exponentially (1 min, 2 min, 4 min…, capped at 1 h)
up to `SCHOLARSHIP_PAYOUT_MAX_ATTEMPTS`. Each payout response includes a
`diagnostics` block (`lastFailure`, `operatorAction`, `attemptsRemaining`,
`nextAutomaticRetryAt`, `canRetry`).

## 4. Receipts

Issued automatically, exactly once per successful payout. Each receipt contains:
receipt number, program name, award and installment ids, recipient id, asset,
amount, network, transaction hash, ledger, memo, source and destination
accounts, completion time, and **evidence links** (Horizon transaction URL and
Stellar Expert URL) so anyone can verify the payment independently.

- Payment facts are write-once, and a schema hook rejects changes and deletes.
  Only the `verifications` history grows:
  `POST /scholarship-finance/receipts/:id/verifications` re-checks the
  transaction on Horizon and appends `verified | mismatch | not_found`.
- Recipients read their own receipts (`GET /scholarship-finance/receipts/me`).
  Organization finance staff read their organization's receipts. Everyone else
  gets `404`, so the response doesn't reveal whether a receipt exists.

## 6. Ownership and authorization

- **Owning team:** Scholarships / Finance backend.
- **Tenant boundary:** every program belongs to exactly one `organizationId`.
  Every lookup filters by both the resource id and the organization (or the
  program), so a valid id from another tenant returns `404`.
- **Who can do what:**
  - Read (`owner`, `admin`, `finance`, `auditor`) and write (`owner`,
    `admin`, `finance`) require an active, non-deleted row in the
    `organizationmembers` collection. This module reads that collection
    through its own read-only model and never writes to it.
  - Platform `admin` users may act on any organization. They are also the only
    callers allowed on the signer endpoints.
  - Recipients can see only their own receipts.

## 7. Privacy

- Stored here: recipient user id, recipient Stellar address, amounts, and
  transaction data. All of it is already public on-chain, apart from the
  mapping to the internal user id.
- **Not stored:** financial-aid or scholarship application content (reasons,
  essays, income, identity documents). Receipts are built only from payout
  facts.
- Receipt and ledger records are financial records and are **not
  soft-deleted or purged**. They are exempt from `SOFT_DELETE_RETENTION_DAYS`,
  because deleting them would break auditability. For erasure requests,
  unlink the user profile elsewhere; the ids here are opaque.

## 8. Migration

New collections, created automatically with their indexes on first boot:

| Collection | Key indexes |
| ---------- | ----------- |
| `scholarship_programs` | `organizationId` |
| `scholarship_ledger_entries` | unique `(organizationId, reference)`, unique sparse `reversalOf`, `(programId, effectiveAt, _id)` |
| `scholarship_payout_intents` | unique `(organizationId, awardId, installmentId)`, `attempts.transactionHash`, `attempts.envelopeHash` |
| `scholarship_payment_receipts` | unique `receiptNumber`, `payoutIntentId`, `transactionHash` |
| `scholarship_reconciliation_runs` | `(programId, createdAt)` |
| `scholarship_reconciliation_alerts` | unique sparse `activeKey`, `(programId, status)` |

There is no backfill: the existing `financial-aid` data is untouched. To move
an existing funded program onto the ledger:

1. Create the program.
2. Post one `funding` entry per historical deposit (or one opening `funding`
   entry with the opening-balance transaction hash).
3. Post `reservation` and `award` entries for outstanding obligations.
4. Run a reconciliation and resolve any drift before issuing new awards.

Aggregations use `$toDecimal`, which requires MongoDB ≥ 4.0.

## 1. Design overview

Every money movement posts to one **append-only, double-entry ledger** scoped per organization (tenant) and per asset.

| Concept | Where | Notes |
| --- | --- | --- |
| Journal | `scholarship_ledger_journals` | Balanced lines; unique `idempotencyKey` per business event; never updated except the `reversedBy` pointer |
| Balance | `scholarship_ledger_balances` | Materialized running balance per `(organizationId, account, assetKey)`, updated with guarded atomic `$inc` |
| Audit | `scholarship_finance_audit` | Every state change: actor, reason, details |

### Chart of accounts

| Account | Side | Meaning |
| --- | --- | --- |
| `asset:custody` | debit | Funds held for the tenant (wallet / bank) |
| `liability:fund:program:<programId>` | credit | Sponsor funds restricted to a program |
| `liability:fund:pool` | credit | Unrestricted scholarship pool |
| `revenue:platform_fee` | credit | Platform fee revenue, **separate from sponsor funds** |
| `liability:network_fee_payable` | credit | Network / rail fees owed to third parties |
| `liability:refund_payable` | credit | Approved refunds awaiting payout |
| `asset:recovery_receivable` | debit | Amounts owed under open recovery claims |
| `contra:recovery_pending` | credit | Memo offset to the receivable until cash is collected |

**Solvency:** no account can go below zero. Postings that would do so fail with `422 BIZ_INSUFFICIENT_FUNDS` before anything is written.

**Amounts:** always integer **minor units** (stroops, cents). Fractions are rejected, not rounded. Fee math uses BigInt.

**Assets:** `{ code, issuer }`, normalized to `assetKey` = `CODE:ISSUER` or `CODE:native`.

## 3. Sponsor deposits & funding rounds (#1166)

| Method | Path | Permission |
| --- | --- | --- |
| POST | `/funding-rounds` | operate |
| GET | `/funding-rounds`, `/funding-rounds/:id` | view |
| POST | `/funding-rounds/:id/close` `{reason}` | approve |
| POST | `/deposits` | operate |
| GET | `/deposits`, `/deposits/:id` | view |
| POST | `/deposits/:id/credit` | approve |
| POST | `/deposits/:id/reject` `{reason}` | approve |
| POST | `/allocation-changes` (requires `X-Idempotency-Key`) | approve |
| GET | `/allocation-changes` | view |

Guarantees:
- **Deposits bind asset and source.** Recording a deposit fixes the asset, the rail and the rail reference (e.g. a Stellar tx hash). A deposit made against a round must use the round's asset (`BIZ_ASSET_MISMATCH`) and goes to the round's allocation.
- **A deposit is never credited twice**, for three reasons:
  1. A unique index on `(source.rail, source.reference, assetKey)` applies across all tenants, so the same transfer can't be recorded twice (`409 BIZ_DEPOSIT_ALREADY_RECORDED`).
  2. Crediting claims the `pending → credited` transition atomically.
  3. The credit journal key is `deposit-credit:<depositId>`.
- **Allocation changes are authorized and auditable.** Only approvers can move funds, and a reason is required. Each move writes an `AllocationChange` record, a journal and an audit event. A move can't take more than the source fund holds.
- **Round closing:** an approver can close a round manually, and the background job closes rounds whose window has ended.

## 4. Fees (#1167)

| Method | Path | Permission |
| --- | --- | --- |
| POST | `/fee-schedules` | approve |
| GET | `/fee-schedules?assetKey=` | view |
| POST | `/fee-schedules/preview` | view |

- **Versioned basis and rounding:**
  - Schedules can't be changed once published. Each one is versioned per tenant and asset, and records its `rounding` (`half_up`, `half_even`, `floor` or `ceil`) and its rules.
  - A rule has a kind (`platform` / `network`), an event, basis points, a fixed fee, and an optional min and max.
  - `effectiveFrom` can't be in the past, so fees never apply retroactively.
- **Every credited deposit records the fees applied:** `fee.feeScheduleId`, `feeScheduleVersion`, the rounding mode and a per-rule breakdown. Fees come from the schedule in force at `receivedAt`.
- **Recipient amounts are never reduced unexpectedly:**
  - For **deposits**, fees are *inclusive*: the program receives `net = gross − fees`, and the preview shows this in advance. If fees would take the whole deposit, the credit is rejected (`BIZ_FEE_EXCEEDS_AMOUNT`) instead of the program silently receiving 0.
  - For **disbursements**, fees are *exclusive*: the recipient receives exactly the requested amount and the program pays `gross = amount + fees`. `FeeService` is exported so the future disbursement module can use the same calculation.
- **Fee revenue is accounted for separately.** Platform fees are credited to `revenue:platform_fee`, and network fees to `liability:network_fee_payable`, never to a fund.
- If no schedule is configured for an asset, fees are zero and the deposit records `feeScheduleVersion: null`.

## 5. Refunds & returned payments (#1168)

| Method | Path | Permission |
| --- | --- | --- |
| POST | `/refunds` | operate |
| GET | `/refunds`, `/refunds/:id` | view |
| POST | `/refunds/:id/approve` | approve (not the requester) |
| POST | `/refunds/:id/complete` `{payoutReference}` | approve |
| POST | `/refunds/:id/reject` `{reason}` | approve |
| POST | `/refunds/:id/cancel` `{reason}` | operate |

| Type | Use | Ledger on approve | Ledger on complete |
| --- | --- | --- | --- |
| `rejected_transfer` | The rail bounced the sponsor's transfer | Full **reversal** of the original credit journal, fees included | none (records the rail return reference) |
| `sponsor_refund` | Sponsor asks for money back | fund → refund payable | refund payable → custody |
| `overpayment` | Sponsor sent too much | fund → refund payable | refund payable → custody |
| `unused_balance` | Money left in a program after its round closed | fund → refund payable | refund payable → custody |

- **Refund authority is restricted.** Only approvers can approve, complete or reject a refund, and the approver can't be the requester.
- **Liabilities stay solvent:**
  - Requests are checked against what is still refundable on the deposit (`net − refunded − pending`).
  - Approval re-checks the deposit atomically, and the ledger guard re-checks the fund. If the credited money has already been moved or spent, approval fails.
- **Original entries are reversed, never deleted:**
  - A rejected transfer posts a mirror journal with `reversalOf` set.
  - Rejecting an already-approved refund posts a reversal of its reservation journal.
  - The deposit status tracks all of this (`partially_refunded`, `refunded` or `reversed`).

## 6. Recoveries & clawbacks (#1169)

| Method | Path | Permission |
| --- | --- | --- |
| POST | `/recoveries` | operate |
| GET | `/recoveries`, `/recoveries/:id`, `/recoveries/:id/collections` | view |
| GET | `/recoveries/reconciliation` | view |
| POST | `/recoveries/:id/approve` | approve (not the author) |
| POST | `/recoveries/:id/collections` | operate |
| POST | `/recoveries/:id/write-off` `{reason}` | approve |
| POST | `/recoveries/:id/cancel` `{reason}` | operate for drafts, approve for open claims |

- **Reason and legal basis are required.** Each claim records a `reason` (`fraud`, `withdrawal` or `milestone_failure`) and a `legalBasis` (`{policyReference, clause, description}`). Evidence is stored as references only.
- **No wallet is ever debited silently:**
  - A claim can only be collected once it has been approved by a second person. Approval sets `noticeIssuedAt` and emits `scholarship-finance.recovery.opened`, which a notification listener should turn into the recipient notice.
  - The collection methods are `voluntary_repayment`, `manual_transfer` and `award_offset` (which requires `recipientConsentRef`). **By design, there is no wallet-debit method.**
  - A collection only records money that has already been received. It needs an `externalReference` that is unique per tenant, and the journal key is derived from that reference, so the same receipt can't be counted twice.
- **Collected amounts reconcile to open claims:**
  - Collections can never exceed `claimed − collected − writtenOff`.
  - `GET /recoveries/reconciliation` checks the following for each asset:
    1. The total outstanding on open claims equals the ledger `recovery_receivable`, which equals the ledger `recovery_pending` contra.
    2. `collectedMinor` summed across claims equals the total of the collection records.
    3. For each claim, `collectedMinor` equals the total of its own collection records.
  - Collected cash goes back to the claim's fund (`custody` debit, fund credit).

## 7. Background jobs & operations

`ScholarshipFinanceJobs` runs on a timer. It is **off by default**.

| Env var | Default | Notes |
| --- | --- | --- |
| `SCHOLARSHIP_FINANCE_JOBS_ENABLED` | `false` | Enable on **one** instance. The jobs are idempotent, so overlapping runs are safe but wasteful. |
| `SCHOLARSHIP_FINANCE_JOB_INTERVAL_MS` | `900000` | Minimum 60000 |

Each run does three things:
1. Closes expired funding rounds.
2. Recomputes every balance from the journals and reports **drift**.
3. Reconciles recoveries for every tenant.

Problems are logged at `error` level and emitted as `scholarship-finance.ledger.drift-detected`. The jobs **only report; they never post corrections.** A platform admin can trigger a run with `POST /scholarship-finance/jobs/run`, and a tenant can check its own ledger with `GET .../ledger/integrity`.

**Consistency model:**
- MongoDB multi-document transactions are not assumed, because deployments may be standalone.
- Each posting runs in this order: guarded balance decrements, then increments, then the journal insert. A failure at any step undoes the balance changes already made.
- Business-state transitions are claimed atomically before posting and rolled back if the posting fails.
- A process crash in the middle of a posting can leave drift. The integrity job exists to catch exactly that. Alert on the drift event, and investigate it by rebuilding from the journals.

**Domain events emitted:** `scholarship-finance.deposit.credited`, `scholarship-finance.refund.completed`, `scholarship-finance.recovery.opened`, `scholarship-finance.ledger.drift-detected`. No listeners are bundled yet. Wiring recipient notices to `NotificationModule` is the recommended follow-up.

## 8. Privacy

- Sponsors and recipients are stored only as opaque ids (`sponsorId`, `recipientId`). No names, emails or bank details are stored.
- For fiat rails, refund destinations should be **tokenized or masked** references (the field is documented this way in the API).
- Recovery evidence is stored as references (document ids / URIs), not as documents.
- The `legalBasis.description` field is free text visible to finance viewers of the tenant. Operators must not put special-category data in it.
- Retention: ledger, audit, deposit, refund and recovery records are financial records and must not be hard-deleted. Handle erasure requests by pseudonymizing the id mapping outside this module.

## 9. Migration impact

- **Additive only.** The module adds new collections (`scholarship_*`) and indexes, which Mongoose creates on boot. No existing collection is changed.
- New optional env vars (see section 7) are registered in `env.validation.ts`.
- Existing organizations gain finance access once members are given one of the `finance_*` roles. Until then, only platform admins can use the endpoints.
- Rollback: remove `ScholarshipFinanceModule` from `AppModule`. The collections can stay in place.
- This change also restores `src/common/decorators/roles.decorator.ts`, which had been overwritten with pasted controller code and had broken every `@Roles` import.
