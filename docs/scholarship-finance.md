# Scholarship Finance

Backend module: `src/scholarship-finance/` (`ScholarshipFinanceModule`).

Covers:

| Issue | Capability |
| ----- | ---------- |
| #1164 | Per-program double-entry ledgers |
| #1165 | Treasury reconciliation, solvency gate, discrepancy alerts |
| #1162 | Payout intents with failure classification and controlled retry |
| #1163 | Durable recipient payment receipts with on-chain evidence |

Interactive API docs are generated by Swagger at `/api` under the
`Scholarship Finance — *` tags.

---

## 1. Domain model

```
Organization (tenant)
└── ScholarshipProgram          one asset, one network, one treasury account
    ├── LedgerEntry*            immutable, balanced journal
    ├── PayoutIntent*           one per (award, installment)
    │   └── attempts[]          one per transaction envelope
    ├── PaymentReceipt*         one per successful PayoutIntent
    ├── ReconciliationRun*      immutable comparison snapshot
    └── ReconciliationAlert*    operator-facing, never edits the ledger
```

Awards and installments are referenced by id (`awardId`, `installmentId`).
This module does not own award eligibility. It only records the money.

### Amounts

All amounts are fixed-point with 7 decimal places (Stellar stroops). The API
accepts and returns decimal strings (`"1250.5"`), and the database stores
integer minor units as strings. Floating point is never used.

### Chart of accounts

| Account          | Normal side | Meaning |
| ---------------- | ----------- | ------- |
| `treasury`       | debit       | Funds held in the program's on-chain treasury account |
| `program_fund`   | credit      | Unencumbered funds available to reserve |
| `reserved`       | credit      | Earmarked for scholarships not yet awarded |
| `awards_payable` | credit      | Awarded to recipients, not yet paid |

Invariant: `treasury = program_fund + reserved + awards_payable`.

### Entry types

| Type                  | Debit            | Credit           | Notes |
| --------------------- | ---------------- | ---------------- | ----- |
| `funding`             | treasury         | program_fund     | requires `transactionHash` |
| `reservation`         | program_fund     | reserved         | **solvency-gated** |
| `reservation_release` | reserved         | program_fund     | |
| `award`               | reserved         | awards_payable   | **solvency-gated**, requires `awardId` |
| `award_cancellation`  | awards_payable   | reserved         | requires `awardId` |
| `disbursement`        | awards_payable   | treasury         | posted automatically by successful payouts |
| `refund`              | program_fund     | treasury         | back to the sponsor, requires `transactionHash` |
| `recovery`            | treasury         | program_fund     | clawback, requires `transactionHash` |
| `adjustment`          | explicit lines   | explicit lines   | requires `reason` (≥ 10 chars) |
| `reversal`            | mirror of original | mirror of original | via the reversal endpoint only |

Rules enforced on every posting:

- sum(debits) = sum(credits) > 0, and every line is > 0.
- `reference` is unique per organization. Replaying an identical request
  returns the original entry with `replayed: true`. Reusing a reference with a
  different payload returns `409 BIZ_LEDGER_REFERENCE_CONFLICT`.
- No account may go negative on its normal side (`BIZ_PROGRAM_INSOLVENT`).
- Postings for a program are serialised with a short-lived lease on the
  program document, so balance checks cannot race.
- Entries are immutable. Mongoose hooks reject update/delete, and corrections
  are made with a reversal plus a new entry. Each entry can be reversed only
  once, and a reversal cannot itself be reversed.
- Suspended programs reject new reservations and awards. Closed programs
  accept only wind-down types (release, cancellation, disbursement, refund,
  recovery, adjustment, reversal).

Balances are always derived from the journal, never stored.

## 2. Reconciliation and solvency

A reconciliation run compares:

- **external**: the treasury account balance from Horizon, or a manual
  snapshot for programs with `externalBalanceSource: "manual"`;
- **ledger**: derived balances as of the run time (entries both effective and
  recorded by then);
- **in-flight**: payouts submitted to the network whose outcome is unknown.

It computes:

- `drift = external − ledger.treasury`. A shortfall up to the in-flight
  amount counts as *explained*; anything else is *unexplained drift*.
- `solvencyMargin = external − explainedDrift − (reserved + awards_payable)`.

Discrepancies (all **critical**):

| Type               | Condition |
| ------------------ | --------- |
| `ledger_integrity` | an entry does not balance, or the accounting identity fails |
| `negative_balance` | any account below zero |
| `balance_drift`    | unexplained drift ≠ 0 |
| `insolvency`       | solvency margin < 0 |
| `payout_posting_failed` | a payout succeeded on-chain but its disbursement could not be posted |

Each discrepancy opens an alert, or refreshes the program's active alert of the
same type (`occurrences`, `lastRunId`). It also emits
`scholarship.reconciliation.alert-raised`. **Alerts never modify the ledger.**
Operators post corrective adjustments or reversals themselves, then resolve
the alert with a note.

**Repeatability.** Runs are immutable and record their inputs: `asOf`, entry
count, last entry id, external balance and source, and in-flight total.
`POST …/reconciliations/:runId/replay` recomputes a run from those inputs and
reports whether every figure matches.

**Solvency gate (before new awards).** Every `reservation` and `award` is
checked by `SolvencyGuardService` before posting. The entry is refused when:

1. an unresolved critical alert exists for the program; or
2. the latest run is missing or older than `SCHOLARSHIP_RECONCILIATION_MAX_AGE_MS`.
   Horizon-backed programs are reconciled inline first. Manual programs must
   record a fresh snapshot; or
3. the latest run found discrepancies; or
4. `min(verified external, ledger treasury) − obligations − new obligation < 0`.

The gate fails closed. If Horizon is unreachable, new awards are refused
(`503 SYS_HORIZON_UNAVAILABLE`).

## 3. Payouts and failure recovery

The backend **never holds signing keys**. A separate custody signer service,
authenticated with a platform-admin token, builds, signs and submits
envelopes, then reports back.

```
operator ── POST payouts ─────────────► intent(pending) + attempt#1(ready)
signer   ── GET  payout-signer/attempts ► instructions (source, destination, asset, amount, memo, maxTime)
signer   ── POST …/attempts/:id/submission  {envelopeHash, transactionHash}  → submitted
signer   ── POST …/attempts/:id/result      {outcome, transactionHash | resultCodes | signerError}
             succeeded → verified on Horizon → disbursement entry → receipt → intent(succeeded)
             failed    → classified → intent(failed) + diagnostics (+ nextRetryAt when automatic)
operator ── POST payouts/:id/retries   {note, destination?} → attempt#n(ready)
```

- **Same intent, new envelope.** Every attempt shares the intent id, amount
  and memo (`SCH-<24 hex>`). An envelope or transaction hash already used by
  any attempt is rejected (`BIZ_PAYOUT_ENVELOPE_REUSED`).
- **No double payment.** A new attempt is created only after the previous one
  is dead: its transaction failed on-chain, or it is absent from Horizon after
  its `maxTime` plus 60s grace. If it succeeded on-chain, the retry is refused
  and the expiry sweep records the success.
- **Eligibility preserved.** Failures and cancellations never touch the award
  or its `awards_payable` balance. Only a verified success posts the
  disbursement.
- **Creation guard.** An intent is accepted only if the award's outstanding
  `awards_payable` covers this amount plus the award's other open intents.

Failure classification (from Horizon `result_codes` or the signer error):

| Category             | Typical codes | Auto retry | Operator action |
| -------------------- | ------------- | ---------- | --------------- |
| `missing_trustline`  | `op_no_trust`, `op_not_authorized`, `op_line_full` | no | recipient adds or authorizes the trustline, then retry |
| `bad_destination`    | `op_no_destination`, `op_malformed` | no | retry **with a corrected destination** (recorded in `destinationHistory`) |
| `insufficient_funds` | `op_underfunded`, `tx_insufficient_balance`, `tx_insufficient_fee`, `op_src_no_trust` | no | top up the treasury, reconcile, retry |
| `network_expiry`     | `tx_too_late`, expired or unsubmitted attempt | yes | none |
| `transient`          | `tx_bad_seq`, `tx_internal_error`, 5xx | yes | none |
| `unknown`            | anything else | no | inspect, then retry |

Automatic retries back off exponentially (1 min, 2 min, 4 min…, capped at 1 h)
up to `SCHOLARSHIP_PAYOUT_MAX_ATTEMPTS`. Each payout response includes a
`diagnostics` block (`lastFailure`, `operatorAction`, `attemptsRemaining`,
`nextAutomaticRetryAt`, `canRetry`).

## 4. Receipts

Issued automatically, exactly once per successful payout. Each receipt contains:
receipt number, program name, award and installment ids, recipient id, asset,
amount, network, transaction hash, ledger, memo, source and destination
accounts, completion time, and **evidence links** (Horizon transaction URL and
Stellar Expert URL) so anyone can verify the payment independently.

- Payment facts are write-once, and a schema hook rejects changes and deletes.
  Only the `verifications` history grows:
  `POST /scholarship-finance/receipts/:id/verifications` re-checks the
  transaction on Horizon and appends `verified | mismatch | not_found`.
- Recipients read their own receipts (`GET /scholarship-finance/receipts/me`).
  Organization finance staff read their organization's receipts. Everyone else
  gets `404`, so the response doesn't reveal whether a receipt exists.

## 5. API summary

All routes require a bearer JWT. Organization-scoped routes also require
tenant membership (see §6).

```
# Programs
POST   /organizations/:orgId/scholarship-programs
GET    /organizations/:orgId/scholarship-programs
GET    /organizations/:orgId/scholarship-programs/:programId
PATCH  /organizations/:orgId/scholarship-programs/:programId/status

# Ledger                     (prefix: /organizations/:orgId/scholarship-programs/:programId)
POST   …/ledger/entries
POST   …/ledger/entries/:entryId/reversals
GET    …/ledger/entries?entryType&awardId&before&limit
GET    …/ledger/entries/:entryId
GET    …/ledger/balances?asOf

# Reconciliation
POST   …/reconciliations                 {externalBalance?, externalObservedAt?}
GET    …/reconciliations
GET    …/reconciliations/:runId
POST   …/reconciliations/:runId/replay
GET    /organizations/:orgId/scholarship-alerts?programId&status
POST   /organizations/:orgId/scholarship-alerts/:alertId/acknowledgement
POST   /organizations/:orgId/scholarship-alerts/:alertId/resolution   {note}

# Payouts
POST   …/payouts                          {awardId, installmentId, recipientId, destination, amount}
GET    …/payouts?status&awardId&limit
GET    …/payouts/:payoutId
POST   …/payouts/:payoutId/retries        {note, destination?}
POST   …/payouts/:payoutId/cancellation   {reason}

# Custody signer (platform admin only)
GET    /scholarship-finance/payout-signer/attempts
POST   /scholarship-finance/payout-signer/payouts/:payoutId/attempts/:attemptId/submission
POST   /scholarship-finance/payout-signer/payouts/:payoutId/attempts/:attemptId/result

# Receipts
GET    /scholarship-finance/receipts/me
GET    /scholarship-finance/receipts/:receiptId
POST   /scholarship-finance/receipts/:receiptId/verifications
GET    /organizations/:orgId/scholarship-receipts?programId&recipientId&limit
```

Every request body and query is validated with Joi. Unknown fields are
rejected rather than stripped, so fields like `organizationId` or `status`
cannot be smuggled in. Errors use the standard `{ message, errorCode }` shape.
New codes are listed in `src/common/errors/error-codes.enum.ts` under
*Scholarship finance*.

## 6. Ownership and authorization

- **Owning team:** Scholarships / Finance backend.
- **Tenant boundary:** every program belongs to exactly one `organizationId`.
  Every lookup filters by both the resource id and the organization (or the
  program), so a valid id from another tenant returns `404`.
- **Who can do what:**
  - Read (`owner`, `admin`, `finance`, `auditor`) and write (`owner`,
    `admin`, `finance`) require an active, non-deleted row in the
    `organizationmembers` collection. This module reads that collection
    through its own read-only model and never writes to it.
  - Platform `admin` users may act on any organization. They are also the only
    callers allowed on the signer endpoints.
  - Recipients can see only their own receipts.

## 7. Privacy

- Stored here: recipient user id, recipient Stellar address, amounts, and
  transaction data. All of it is already public on-chain, apart from the
  mapping to the internal user id.
- **Not stored:** financial-aid or scholarship application content (reasons,
  essays, income, identity documents). Receipts are built only from payout
  facts.
- Receipt and ledger records are financial records and are **not
  soft-deleted or purged**. They are exempt from `SOFT_DELETE_RETENTION_DAYS`,
  because deleting them would break auditability. For erasure requests,
  unlink the user profile elsewhere; the ids here are opaque.

## 8. Migration

New collections, created automatically with their indexes on first boot:

| Collection | Key indexes |
| ---------- | ----------- |
| `scholarship_programs` | `organizationId` |
| `scholarship_ledger_entries` | unique `(organizationId, reference)`, unique sparse `reversalOf`, `(programId, effectiveAt, _id)` |
| `scholarship_payout_intents` | unique `(organizationId, awardId, installmentId)`, `attempts.transactionHash`, `attempts.envelopeHash` |
| `scholarship_payment_receipts` | unique `receiptNumber`, `payoutIntentId`, `transactionHash` |
| `scholarship_reconciliation_runs` | `(programId, createdAt)` |
| `scholarship_reconciliation_alerts` | unique sparse `activeKey`, `(programId, status)` |

There is no backfill: the existing `financial-aid` data is untouched. To move
an existing funded program onto the ledger:

1. Create the program.
2. Post one `funding` entry per historical deposit (or one opening `funding`
   entry with the opening-balance transaction hash).
3. Post `reservation` and `award` entries for outstanding obligations.
4. Run a reconciliation and resolve any drift before issuing new awards.

Aggregations use `$toDecimal`, which requires MongoDB ≥ 4.0.

## 9. Operations

Environment variables (all optional):

| Variable | Default | Purpose |
| -------- | ------- | ------- |
| `STELLAR_HORIZON_URL_TESTNET` | `https://horizon-testnet.stellar.org` | Horizon for testnet programs |
| `STELLAR_HORIZON_URL_PUBLIC` | `https://horizon.stellar.org` | Horizon for public-network programs |
| `STELLAR_HORIZON_TIMEOUT_MS` | `10000` | Horizon request timeout |
| `SCHOLARSHIP_RECONCILIATION_INTERVAL_MS` | `3600000` | scheduled reconciliation (0 disables) |
| `SCHOLARSHIP_RECONCILIATION_MAX_AGE_MS` | `3600000` | staleness limit for the solvency gate |
| `SCHOLARSHIP_PAYOUT_RETRY_INTERVAL_MS` | `60000` | expiry sweep and auto-retry job (0 disables) |
| `SCHOLARSHIP_PAYOUT_MAX_ATTEMPTS` | `5` | attempts per payout intent |
| `SCHOLARSHIP_PAYOUT_ENVELOPE_TTL_SECONDS` | `300` | `maxTime` time bound given to the signer |

- **Jobs** run in-process (`ScholarshipFinanceJobs`), are disabled when
  `NODE_ENV=test`, never overlap within a process, and are idempotent, so
  running them on several replicas is safe.
- **Events** for notifications and monitoring:
  `scholarship.ledger.entry-posted`, `scholarship.payout.attempt-ready`,
  `scholarship.payout.failed`, `scholarship.payout.succeeded`,
  `scholarship.receipt.issued`, `scholarship.reconciliation.completed`,
  `scholarship.reconciliation.alert-raised`.
- **Logs:** alerts log at `error` with an `[ALERT]` prefix, and payout
  failures log at `warn` with their category. Wire both into paging.
- **Horizon outage:** new awards are blocked (fail closed). Payout success
  reports return `422` or `503` and the signer retries. Existing data is
  unaffected.
- **Runbook: drift alert.** Compare the run's `inputs` and `results`, find the
  missing or extra on-chain movement, post the corrective entry (for example a
  `funding` entry with its tx hash, or an `adjustment` with a reason), re-run
  reconciliation, then resolve the alert with a note naming the corrective
  entry.
